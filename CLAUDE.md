# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project overview

`rst-sphinx-ci` is a docs-as-code reference project. It pairs a small Python tool, **USD Scene Inspector**
(`usd_inspect`), with a complete documentation pipeline: Sphinx and reStructuredText, generated API reference,
tested code samples, automated quality checks in CI, publishing to GitHub Pages, and AI-ready output.

The documentation pipeline is the point of the project. The tool exists to give the docs real code to document
and test. Keep the tool small and the pipeline excellent.

## Definition of done

The project is complete when every item below is true. Do not describe any item as done (in the README, docs,
or commit messages) until it actually works.

- [x] `usd_inspect` reads a `.usda`/`.usd` file with Pixar's `usd-core` package and:
  - lists prims with their paths and types
  - lists attributes and values for a prim
  - flags references and payloads whose target files are missing
- [x] A command-line entry point (`usd-inspect <file>`) exposes those features.
- [x] Test scenes in `examples/scenes/` are generated by `scripts/make_scenes.py`, including one with a
      deliberately broken reference.
- [x] Sphinx docs in `docs/source/`, written in reStructuredText:
  - overview, installation, quick start, CLI usage, and a page explaining the docs pipeline itself
  - a test scenes page that describes each generated scene
  - a glossary of USD terms (prim, layer, reference, payload, composition arc), linked from other pages with
    `:term:`
  - API reference generated with `sphinx.ext.autodoc` from docstrings
  - code samples validated with `sphinx.ext.doctest` against the generated scenes
  - a full table-of-contents sidebar on every page, plus an "On this page" sidebar
  - admonitions (`note`, `important`, `warning`, `tip`) used in real content
  - `sphinx-design` tabs where instructions differ by platform
  - a section on the pipeline page that points to each rST feature the docs use
- [x] GitHub Actions on every pull request to `develop` or `main`:
  - `sphinx-build -W` (warnings fail the build)
  - `make doctest`
  - `make linkcheck`
  - Vale style linting of `docs/source`, `README.md`, `src`, and `scripts`, with spelling errors failing the build
  - `pytest`
- [x] A demonstration pull request shows the Vale check failing on a deliberate typo, then passing after the fix.
- [x] Merges to `main` publish the built site to GitHub Pages.
- [x] `main` is protected: changes arrive by pull request with passing checks.
- [x] Stretch: `scripts/build_llms_txt.py` generates `llms.txt` and `llms-full.txt` from the built site.
- [x] Stretch: `evals/` holds question-and-answer pairs, plus a script that checks an LLM's answers against the
      docs.

## Conventions

### Documentation
- Write all docs pages in reStructuredText (`.rst`), not Markdown. `README.md` is the only Markdown file.
- Use Sphinx roles for cross-references (`:doc:`, `:ref:`, `:py:func:`, `:py:class:`) rather than raw links, so
  the build validates them.
- Every Python code sample a reader might copy must be a doctest that runs in CI. Use the `SCENES` path defined in
  `doctest_global_setup` in `conf.py`; never hard-code absolute paths. Shell commands use `code-block`.
- Use admonitions (`note`, `important`, `warning`, `tip`) where they help the reader, not as decoration.
- Docstrings use Google style, rendered with `sphinx.ext.napoleon`.
- Write plainly and in second person. Prefer short sentences and task-oriented headings.

### Code
- Python 3.11+. Keep `usd_inspect` small and readable; this is a documentation showcase, not a framework.
- Verify every USD API call by running it. Do not guess `pxr` method names or signatures; if unsure, check the
  OpenUSD API docs or inspect the object in a Python session before writing the code.
- Add or update tests and doctests in the same change as the code they cover.

### Test scenes and third-party assets
- Use only scenes generated by `scripts/make_scenes.py`. Regenerate them with the script; do not hand-edit the
  `.usda` files.
- Do not add, download, or reference third-party USD assets in the repo, docs, or CI. In particular, never use
  Pixar's Kitchen Set or City Set: their license forbids redistribution and derivative works.
- Do not use company names, product names, logos, or assets other than Pixar's open-source `usd-core` library,
  which is a declared dependency.

### Git workflow
- Branch from `develop` with `feature/<short-name>`. Open a pull request into `develop`.
- Release by pull request from `develop` into `main`.
- Keep commits small and focused, with imperative-mood messages ("Add doctest for prim listing").
- Commits are signed automatically (SSH signing is configured). Never disable signing.
- Never force-push `main` or `develop`. Never commit `docs/build/`, virtual environments, or caches.

## Working with the maintainer

- Propose a short plan before multi-file changes, and wait for approval on anything that changes the definition
  of done, the repo layout, or the CI workflow.
- Run the relevant checks locally before saying a change is finished, and report the actual results.
- Explain what you changed and why in a few lines. Flag anything you were unsure of instead of guessing.
- The maintainer reviews every change before it merges. Optimize for changes that are easy to review.

## Common commands

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[docs,test]"            # required before building docs: conf.py reads the package version

python scripts/make_scenes.py            # regenerate test scenes

sphinx-build -W -b html docs/source docs/build/html
sphinx-build -b doctest docs/source docs/build/doctest
sphinx-build -b linkcheck docs/source docs/build/linkcheck
vale sync                                # once: download the Google style into styles/
vale docs/source README.md src scripts
python scripts/build_llms_txt.py         # after the HTML build: llms.txt, llms-full.txt, page .md files
python evals/run_evals.py                # needs ANTHROPIC_API_KEY and .[evals]; never in CI
pytest
```

Decisions made so far:

- Theme: `pydata-sphinx-theme`, the open-source base of the reference project's theme. Don't use the vendor's own
  theme package; its license restricts it to the vendor's products.
- Vale: the `Vale` and `Google` styles plus a custom vocabulary for USD terms. `Vale.Spelling` is the typo gate; no
  separate spell checker. `Vale.Terms` is off for `.py` files because docstrings mention `.usd` and `usd-core`.
- Linkcheck: non-blocking on pull requests, plus a weekly scheduled run that must pass.
- Branch protection: protect `main` only. The maintainer runs the `gh api` command, which Claude drafts after the CI
  job names exist.
- Evals (stretch): run locally against the Claude API and commit the results. No API key in CI.
- `llms.txt`: generated by our own script from the built HTML, not a Sphinx extension. Sphinx's `text` builder was
  rejected: it wraps at 70 characters (splitting `usd-core`) and leaves markup. The pipeline page is under
  `## Optional`.
